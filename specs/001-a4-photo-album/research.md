# Research: A4 사진 앨범 페이지 만들기

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Date**: 2026-10-06

Technical Context의 미정 항목과 핵심 리스크를 결정한 기록이다. 검증 스파이크는 이 PC(Windows 11, Python 3.14.6)에서 실행했다.

## R1. 구현 언어와 실행 형태

- **Decision**: Python 3.10+ 스크립트 1개(`scripts/make_album.py`)를 본체로 한다. 실행은 `python scripts/make_album.py <폴더>`.
- **Rationale**: 사용자가 원한 "exe 없이 스크립트 몇 개"에 맞는다. 이 PC에 Python 3.14와 Pillow가 이미 있고, PDF·이미지 라이브러리가 가장 성숙하다. 코드가 짧아 사용자가 직접 읽고 고칠 수 있다.
- **Alternatives considered**:
  - PowerShell 단독: Windows 기본 탑재지만 PDF 생성·이미지 원본 삽입 기능이 없어 결국 외부 도구가 필요하다.
  - Node.js(+pdf-lib): 가능하지만 EXIF 처리·이미지 검사 생태계가 Python보다 약하다.
  - HTML+브라우저 인쇄: 인쇄 배율·여백이 브라우저 설정에 좌우되어 FR-002(100% A4) 보장이 어렵다(Q4에서 PDF로 결정).

## R2. PDF 생성 라이브러리 (FR-002, FR-002a, SC-007)

- **Decision**: `reportlab` (BSD). `rl_config.useA85 = 0`으로 두고 JPEG는 파일 경로로 `drawImage`에 넘긴다.
- **Rationale**: 스파이크 결과, 4000×3000 JPEG가 `/DCTDecode` 스트림으로 **원본 파일과 바이트 단위로 동일하게** 들어갔다(188,628 bytes = 188,628 bytes). 즉 재압축·축소가 전혀 없다. 기본값(ASCII85 켜짐)에서는 바이트가 달라지지만 이는 텍스트 인코딩일 뿐 손실은 없다. 다만 용량이 25% 늘어 끈다. PNG는 Flate(무손실)로 들어가며 픽셀이 같다. 캔버스 좌표 변환(회전·반전)을 자유롭게 쓸 수 있어 R4의 EXIF 처리에 필요하다. TTF 글꼴 서브셋 임베딩도 된다.
- **Alternatives considered**:
  - PyMuPDF(`fitz`, 이미 설치됨): JPEG 원본 삽입은 되지만 AGPL 라이선스이고, 좌우 반전 EXIF(2/4/5/7)를 처리할 방법이 마땅치 않다. 대신 **테스트에서 PDF를 검사하는 용도**로 쓴다.
  - fpdf2: JPEG 원본 삽입과 변환이 되지만, reportlab만큼 검증해 볼 여유가 없었고 이점도 없다.
  - img2pdf: 원본 삽입에 특화됐지만 텍스트(메모 라벨)를 그릴 수 없다.

## R3. 한글·이모지 글꼴 (FR-012)

- **Decision**: 기본 글꼴은 맑은 고딕(`C:\Windows\Fonts\malgun.ttf`)이다. 맑은 고딕에 없는 글자는 Segoe UI Emoji(`seguiemj.ttf`)를 거쳐 Segoe UI Symbol(`seguisym.ttf`) 순으로 대체한다(글자 단위). 대체 글꼴 어디에도 없는 글자는 경고를 낸다. 글꼴 경로는 `--font` 옵션으로 바꿀 수 있다.
- **Rationale**: 스파이크에서 맑은 고딕이 서브셋으로 임베딩되고 "벚꽃 축제 모습"이 정상 추출됐다. 이모지는 Segoe UI Emoji의 흑백 윤곽으로 그려진다. PDF 텍스트 추출은 깨질 수 있지만 인쇄물에는 영향이 없다. 컬러 이모지는 범위 밖이다.
- **Alternatives considered**: 나눔 글꼴 동봉은 저장소 용량과 라이선스 표기 부담만 늘린다. 모든 Windows에 맑은 고딕이 있다.

## R4. 사진 회전 정보(EXIF Orientation) 처리 (FR-013 + FR-002a)

- **Decision**: 픽셀은 손대지 않고 PDF 그리기 좌표 변환으로 방향을 맞춘다. Pillow로 Orientation(1~8) 값만 읽는다. 5~8은 가로·세로가 바뀌므로, 배치 크기를 계산할 때 표시 기준(회전 후) 가로세로를 쓴다.
- **Rationale**: Pillow로 회전해서 다시 저장하면 재압축이 일어나 FR-002a에 어긋난다. 좌표 변환만 하면 원본 JPEG 바이트를 그대로 유지하면서 바르게 보인다. 이 방법은 스파이크에서 `rotate(90)`으로 확인했다.

## R5. 메모 라벨 배치 기하 (FR-005, FR-006, FR-007)

- **Decision**: 수치는 다음과 같다(단위 mm). 구현 중 육안 확인 후 돌출량을 14/8에서 10/5로 줄였다. 처음 값에서는 한 줄 라벨이 사진과 약 2mm만 겹쳐 "걸친" 느낌이 약했다.
  - 페이지는 210×297이고 여백은 사방 10mm다. 칸 2개는 각각 190×133.5(칸 사이 간격 10)다.
  - **라벨 돌출 여유**를 둔다. 칸에서 오른쪽 10, 위쪽 5을 비워 둔 나머지(180×128.5) 안에 사진을 비율 그대로 최대로 맞추고, 그 상자 안에서 가운데 정렬한다.
  - 라벨은 오른쪽 위 꼭짓점이 "사진 오른쪽 위 모서리 + (10, 5)"에 오도록 둔다. 사진 바깥으로 오른쪽 10mm, 위로 5mm만큼 튀어나온다.
  - 라벨 너비는 내용에 따라 최소 30mm, 최대 64mm다. 글꼴은 11pt로 시작하고 최대 3줄까지 줄바꿈한다. 3줄에 안 들어가면 글꼴을 1pt씩 최소 8pt까지 줄인다. 그래도 안 되면 끝을 "…"로 자르고 경고한다.
  - 겹침 면적은 (라벨 너비 − 10) × (라벨 높이 − 5)이다. 이 값이 사진 면적의 15%를 넘으면 글꼴을 줄이고, 그래도 넘으면 줄 수를 줄인다(FR-005).
  - 라벨 모양은 흰색(#FFFFFF) 바탕(변경 요청으로 연노랑에서 바꿈), 얇은 회색 테두리, 오른쪽 아래로 1mm 옅은 그림자를 둔 직사각형이다. 기울이지 않는다.
- **Rationale**: 돌출 여유를 칸 안에 미리 확보하므로 사진이 칸 너비를 꽉 채워도 라벨이 페이지 밖으로 잘리지 않는다(Edge Case). 최악의 경우로 세로 사진(약 96×128.5mm)에 3줄 라벨(64×약 20mm)이 붙어도 겹침은 54×15 ≈ 815mm²(사진의 약 7%)로 15%보다 훨씬 작다.
- **Alternatives considered**: 라벨을 3° 기울이면 더 "메모" 같지만 경계 계산이 복잡해지고 잘림 위험이 생긴다. 나중에 옵션으로 추가할 수 있다.

## R6. 정렬과 설명 추출 (FR-001a, FR-004)

- **Decision**:
  - 설명은 확장자를 뺀 이름(stem)에 `^\d+_` 정규식을 한 번만 적용해 떼어 낸다. 그 뒤 앞뒤 공백을 지운다.
  - 정렬 키는 이름을 `(\d+)`로 쪼갠 자연 정렬(숫자 조각은 int, 글자 조각은 casefold)이다. 키가 같으면 원래 이름 순서로 정한다.
- **Rationale**: "2_바다" < "10_산"이 된다. 숫자가 같으면 뒤 텍스트순이고, 숫자 접두어가 없는 이름은 숫자로 시작하는 이름 뒤에 온다. "3_엄마_아빠"는 "엄마_아빠"가 된다(맨 앞 한 번만 뗌).

## R7. 입력 파일 판별과 오류 처리 (FR-009, FR-010)

- **Decision**:
  - 대상은 폴더 바로 아래의 `.jpg`, `.jpeg`, `.png`(대소문자 무시) 파일이고, 하위 폴더는 보지 않는다.
  - 확장자가 아니라 **실제 형식**으로 판단한다. JPEG·MPO·PNG는 그대로 넣고, 그 밖에 열리는 형식(`.heic/.heif/.avif/.webp/.gif/.bmp/.tif(f)`, 이름만 `.jpg`인 다른 형식 포함)은 임시 폴더에서 변환한다. 첫 장면만 쓰고 바른 방향으로 세운다(`exif_transpose`). pillow-heif는 HEIC 회전을 디코딩할 때 이미 적용하므로 이중 회전이 없다.
  - 변환 대상 형식은 내용에 따라 고른다. 색이 256개 이하이거나 투명 부분이 있으면 PNG(무손실), 그 밖의 사진은 JPEG 품질 95(4:4:4)다. 변환은 "알림"으로 보고하며 경고 건수에는 넣지 않는다.
  - 카메라 RAW(`.cr2/.cr3/.nef/.arw/.dng/.orf/.rw2/.raf`)는 "지원하지 않는 사진 형식" 경고를 내고 건너뛴다.
  - 그 밖의 파일과 숨김 파일(`.`으로 시작, 숨김 속성, `Thumbs.db`, `desktop.ini`)은 조용히 무시한다.
  - 각 사진은 Pillow `open()` + `verify()`로 검사하고, 실패하면 "열 수 없는 사진" 경고를 내고 건너뛴다.
  - 저해상도 경고는 인쇄 크기 기준 유효 해상도가 150dpi 미만일 때 낸다.
- **Rationale**: 처음에는 HEIC 등을 건너뛰기로 했지만, 변경 요청에 따라 스크립트가 직접 변환한다. PDF가 그대로 담을 수 있는 사진 형식은 JPEG(DCT)와 무손실 래스터(Flate, 즉 PNG와 같은 방식)뿐이라 둘 중 하나로 바꿔야 한다. 실측(실제 사진 3000×1688, Windows 배경화면 img102 기반)은 다음과 같다.

  | 원본 | 원본 MB | JPEG95 PDF MB | PSNR | PNG PDF MB | PSNR |
  |------|--------|---------------|------|------------|------|
  | HEIC(사진) | 1.53 | 0.80 | 50.0dB | 3.34 | ∞ |
  | WEBP 손실(사진) | 0.18 | 0.57 | 50.5dB | 1.71 | ∞ |
  | WEBP 무손실 / BMP / TIFF(사진) | 2.34 / 16.88 / 7.25 | 0.81 | 49.6dB | 4.11 | ∞ |
  | GIF / BMP(그래픽, 단색 도형+글자) | 0.02 / 4.80 | 0.09 | 57.8dB | 0.02 | ∞ |

  - 사진에서는 JPEG 95가 PNG보다 4–5배 작다. PSNR 약 50dB는 눈으로 구별할 수 없는 수준(보통 40dB 이상)이다.
  - 그래픽에서는 PNG가 더 작고 손실도 없다. JPEG는 글자·경계선 주변에 번짐이 생긴다.
  - 그래서 "무조건 JPEG"가 아니라 내용에 따라 고른다.
  - JPEG 2000(JPX)도 PDF에 들어가지만 reportlab이 지원하지 않고 뷰어 호환성도 낮아 제외했다.

## R8. 출력 위치

- **Decision**: 기본 출력은 사진 폴더의 **부모 폴더**에 `<폴더이름>_album.pdf`로 만든다. `-o/--output`으로 바꿀 수 있다. 이미 있으면 덮어쓴다(다시 실행하면 새로 만든다는 User Story 2와 같다).
- **Rationale**: 사진 폴더 안에 쓰지 않으므로 원본 폴더가 깨끗하게 유지된다(FR-002a의 취지). 다시 실행할 때 PDF가 입력으로 섞일 걱정도 없다.

## R9. Claude Code 바로가기 (FR-011a)

- **Decision**: 프로젝트 스킬 `.claude/skills/album/SKILL.md`를 만든다. 호출은 `/album <폴더>`. 스킬은 의존성 확인(필요하면 `pip install -r requirements.txt` 안내) → 스크립트 실행 → 표준 출력의 PDF 경로와 경고를 그대로 사용자에게 전달하는 일만 한다.
- **Rationale**: 앨범 내용은 스크립트만 결정하므로, 두 실행 방법의 결과가 같다(SC-002).

## R10. 테스트 방식

- **Decision**: pytest를 쓴다. 테스트 사진은 Pillow로 그때그때 만든다(EXIF Orientation을 포함한 JPEG, 투명 PNG, 깨진 파일). 만든 PDF는 PyMuPDF로 검사한다. 검사 항목은 페이지 수, 페이지 크기, 이미지 스트림이 원본 JPEG 바이트와 같은지, 라벨 텍스트, 그리고 이미지·라벨 사각형이 여백 안에 있는지와 겹침 비율이다.
- **Rationale**: 성공 기준 SC-001/004/006/007을 자동으로 검증할 수 있다. SC-005(클리어 파일에 넣은 모습)는 quickstart의 수동 확인으로 남긴다.
